# MikroTik Fleet Manager — backend

Мультитенантный бэкенд для настройки и мониторинга парка роутеров MikroTik
через RouterOS REST API (RouterOS v7+, включите `www-ssl` в `/ip services`
на каждом роутере).

## Стек

- **API**: Fastify + TypeScript
- **БД**: PostgreSQL + TimescaleDB (метрики CPU/памяти/трафика — hypertables)
- **Очередь опроса**: BullMQ + Redis (отдельный воркер, не блокирует API)
- **Auth**: JWT, роли `admin` / `operator` / `viewer`, всё скоуплено по `tenant_id`

## Быстрый старт

```bash
cp .env.example .env
# отредактируйте .env: смените POSTGRES_PASSWORD, JWT_SECRET
# и сгенерируйте MASTER_KEY:
openssl rand -hex 32   # вставьте результат в MASTER_KEY

docker compose up --build -d
```

Если в `.env` заданы `BOOTSTRAP_ADMIN_USERNAME`/`BOOTSTRAP_ADMIN_PASSWORD`,
при первом старте (когда таблица `users` ещё пуста) под них автоматически
создаётся тенант и admin-аккаунт — больше ничего делать не нужно, сразу
входите в веб-интерфейс. Если эти переменные не заданы, создайте первого
пользователя вручную:

```bash
# создать демо-тенанта, admin-пользователя (admin/admin123) и один пример роутера
docker compose exec api node dist/scripts/seed.js
```

API поднимется на `http://localhost:3000`, веб-интерфейс — на
`http://localhost:5173`, Adminer (просмотр БД) — на `http://localhost:8080`
(сервер: `postgres`, логин/пароль из `.env`).

Откройте `http://localhost:5173`, войдите под настроенным bootstrap-логином
(или `admin` / `admin123`, если использовали сид-скрипт) — увидите карточки
роутеров, кликните на роутер, чтобы открыть вкладки мониторинга/firewall/
DHCP/Wi-Fi/настроек. Недоступные роутеры мигают красным (карточка и статус
интерфейса) — список обновляется раз в 10 секунд.

**Разворачиваете не на своей машине, а на удалённом сервере?** Фронтенд сам
определяет адрес API по адресу страницы (тот же хост, порт 3000) — просто
открывайте `http://<IP-или-домен-сервера>:5173`, ничего пересобирать не
нужно. Задавать `VITE_API_URL` вручную (build arg во `frontend` в
`docker-compose.yml`) нужно, только если API живёт на другом хосте/порту,
например за отдельным доменом и reverse-proxy.

## Аутентификация

```bash
curl -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
# -> { "token": "..." }
```

Дальше передавайте `Authorization: Bearer <token>` во всех запросах.

## Основные эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/routers` | добавить роутер (креды шифруются AES-256-GCM) |
| GET | `/routers` | список роутеров тенанта |
| POST | `/routers/:id/test` | проверить связь с роутером |
| GET | `/routers/:id/metrics?hours=24` | история CPU/памяти для графиков |
| GET | `/routers/:id/interface-metrics?hours=24` | история трафика по интерфейсам |
| GET | `/routers/:id/interfaces` | live-список интерфейсов |
| GET/POST/PATCH/DELETE | `/routers/:id/firewall/filter` | правила firewall |
| GET | `/routers/:id/dhcp/leases` | DHCP-аренды |
| GET | `/routers/:id/wifi/clients` | подключённые Wi-Fi клиенты |
| GET/POST | `/routers/:id/config?path=...` | универсальный доступ к любому меню RouterOS (VPN, Queues, Bridge, Scripts и т.д.) |

`/routers/:id/config` — то, что закрывает требование "настраивать все
элементы RouterOS": вместо отдельного route на каждую из сотен сущностей
RouterOS, это прямой проброс к любому пути `/rest/...`. Пример:

```bash
curl -X POST http://localhost:3000/routers/<id>/config \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"path":"/ip/firewall/nat","method":"put","data":{"chain":"srcnat","action":"masquerade","out-interface":"ether1-wan"}}'
```

Каждый мутирующий вызов пишется в `audit_log` (кто, когда, что изменил).

## Как работает опрос (мониторинг)

Воркер (`worker` сервис в compose) раз в `POLL_INTERVAL_MS` (по умолчанию
15 сек) проходит по всем роутерам во всех тенантах, тянет
`/system/resource` и `/interface`, пишет точки в `router_metrics` и
`interface_metrics` (TimescaleDB hypertables, retention 14 дней), и
обновляет `routers.status` (`up` / `warn` / `down`). Фронтенд может
опрашивать `/routers` раз в несколько секунд, чтобы получать live-статус
для мигающих индикаторов отвала — либо позже добавить WebSocket-релей
поверх Redis pub/sub (воркер уже пишет статус в Postgres, событие можно
транслировать оттуда).

## Безопасность

- Пароли роутеров хранятся зашифрованными (AES-256-GCM, ключ — `MASTER_KEY`, не в БД)
- На каждом роутере — отдельный API-пользователь с ограниченной группой прав, не `admin`
- REST API роутера — только `www-ssl`, доступ ограничен firewall'ом роутера до IP этого сервера
- Все мутирующие операции аудируются в `audit_log`
- Роли `viewer`/`operator`/`admin` ограничивают, что можно менять

## Выбор наблюдаемых интерфейсов

Во вкладке «Мониторинг» — чеклист всех интерфейсов роутера. Отмеченные
чекбоксом считаются «наблюдаемыми»:
- статус роутера (`up`/`warn`/`down`) считается по ним (если ничего не
  выбрано — по всем интерфейсам, как раньше)
- график трафика (Rx/Tx, kbps) строится только по выбранным
- воркер по-прежнему пишет метрики раз в `POLL_INTERVAL_MS`, но если список
  выбран — сохраняет только по этим интерфейсам (меньше лишних данных в
  Timescale)

Строка интерфейса, который реально «отвалился» (не disabled, но не
running), мигает красным — как и карточки роутеров на дашборде.

## Дашборды «Топ клиентов»: Wi-Fi и Ethernet

Два отдельных раздела на роутере с CAPsMAN/бриджем — специально разделены,
чтобы поломка одного источника данных не гасила другой (так было раньше,
когда они жили в одной таблице).

### Топ Wi-Fi

Как и раньше — источники:
- **CAPsMAN registration-table** — какие клиенты (по MAC) подключены к
  каким точкам доступа, накопительные счётчики байт (скорость считается по
  дельте между опросами). IP — из `last-ip` самой таблицы, DHCP/ARP —
  запасной вариант. Формат `bytes` (`"rx,tx"`) подтверждён на реальных
  данных.
- **Локальный Wi-Fi без CAPsMAN** — если CAPsMAN не настроен (или на нём
  сейчас нет клиентов), автоматически используется собственная
  registration-table роутера (`/interface/wifi/registration-table`, а если
  её нет — legacy `/interface/wireless/registration-table`). Те же данные
  по сути, просто без контроллера — работает «из коробки» для одиночных
  точек доступа. Единственное отличие в полях: у локальной таблицы нет
  `last-ip`/`remote-cap-identity`, поэтому IP целиком берётся из DHCP/ARP, а
  в качестве «точки доступа» показывается сам локальный интерфейс.
- **DHCP-аренды** и **ARP** — имя хоста и IP

### Топ Ethernet — без Simple Queue

Собирается из:
- **Bridge host table** (`/interface/bridge/host`) — какой MAC выучен на
  каком физическом порту
- **Neighbor Discovery** (`/ip/neighbor`) — виден ли на порту другой
  MikroTik/свитч (тогда это аплинк, а не конечный клиент)
- Счётчики самого порта (`rx-byte`/`tx-byte`) — та же дельта, что и в
  мониторинге интерфейсов

Логика:
- Если на порту виден **ровно один** MAC — трафик порта честно приписывается
  этому устройству (метка «точно»)
- Если MAC-адресов несколько, или порт ведёт к другому MikroTik/свитчу —
  показывается как **общий порт** или **сосед**, с агрегированным трафиком
  порта, без придуманных цифр на конкретное устройство

**Ограничение осталось**: устройства за общим (не изолированным) портом
без соседа через Neighbor Discovery в принципе нельзя разделить без
Simple Queue/accounting/Torch — это архитектурный предел RouterOS, а не
баг. Простые queue тоже можно настроить (метод `getSimpleQueues` в
`mikrotik/client.ts` оставлен, просто сейчас не используется) — дайте
знать, если хотите его подключить как ещё один источник.

## Управление пользователями

Кнопка **«Пользователи»** в шапке (видна только `admin`) — список
пользователей тенанта, добавление новых (логин/пароль/роль), смена роли,
сброс пароля, удаление. Новые пользователи видят те же роутеры и графики,
что и админ — доступ ограничен только ролью:
- `viewer` — только просмотр
- `operator` — просмотр + изменения (firewall, настройки роутеров)
- `admin` — полный доступ, включая управление пользователями

Кнопка **«Сменить пароль»** видна всем — самостоятельная смена своего
пароля с проверкой текущего.

## Детали клиента Wi-Fi

Кнопка **«Детально»** на карточке в «Топ Wi-Fi» открывает окно с максимумом
данных по конкретному устройству:

- **Кто это** — имя хоста (DHCP), производитель по MAC (OUI). Определение
  производителя идёт через внешний сервис `api.macvendors.com` **по
  запросу** (не во время фоновых опросов), с кэшированием результата в
  таблице `mac_vendors` — повторный лукап того же OUI больше не бьёт наружу.
  Если у контейнера `api` нет доступа в интернет — поле просто покажет
  «неизвестен», это не ошибка.
- **Когда подключился** — берётся `uptime` из живого снимка registration
  table (CAPsMAN или локальный Wi-Fi) на момент открытия окна, пересчитан в
  «подключён с (дата) · (длительность)»
- **Скорость канала** — PHY-скорость Rx/Tx (`rx-rate`/`tx-rate`) как есть от
  роутера, сигнал в dBm
- **Куда ходит** — топ-10 адресов назначения из таблицы отслеживания
  соединений (`/ip/firewall/connection`), агрегировано по IP, с best-effort
  обратным DNS (не более ~0.7 сек на адрес, при неудаче — просто IP)
- **График трафика за 24ч** — из уже накопленной истории `wifi_client_metrics`

Требует, чтобы conntrack на роутере был активен (обычно включён по
умолчанию, если настроен firewall/NAT) — иначе раздел «куда ходит» будет
пустым.

## Firewall: счётчики и эвристика «узкого места»

RouterOS уже отдаёт `bytes`/`packets` в стандартном ответе `/ip/firewall/filter`
— ничего дополнительно опрашивать не пришлось. Добавлено:
- Колонки Packets/Bytes и скорость (bps/pps) — считается на фронте по
  разнице между двумя обновлениями (появится после второго опроса,
  автообновление настраивается: 5с/15с/1мин)
- Статус: «не сработало» (packets=0), «активно» (растёт прямо сейчас),
  «сейчас тихо» (были пакеты, но не растут с последнего опроса)
- Эвристика **«⚠️ возможное узкое место»**: правило стоит во второй половине
  своей цепочки (после многих других) и через него проходит заметная доля
  пакетов этой цепочки — стоит проверить, не стоит ли поднять его выше.
  Это именно эвристика по порядку и объёму трафика, не полноценный профайлинг
  CPU (`/tool profile` было бы точнее, но REST его не предоставляет).

## DHCP: «в сети с» + связка с Wi-Fi трафиком

Раньше RouterOS не хранит, когда MAC/IP появился в сети — только текущую
аренду. Добавлена собственная таблица `dhcp_first_seen`: воркер на каждом
опросе делает upsert (первое появление фиксируется один раз, последнее
обновляется всегда). Колонка «В сети с» появилась в самой вкладке DHCP.

В **деталях клиента Wi-Fi** (кнопка «Детально» в «Топ Wi-Fi») это
связывается с фактическим трафиком:
- **«В сети с (DHCP)»** — когда впервые увидели MAC/IP по DHCP
- **«Начал генерировать трафик»** — момент первой ненулевой метрики
  трафика для этого MAC в `wifi_client_metrics` (может быть позже, чем
  DHCP — устройство получило адрес, но не сразу начало слать/принимать
  данные)

## Разбивка трафика по каналам — убрана (была слишком дорогой)

Первая версия классифицировала трафик клиента (внутренняя сеть/провайдер/
VPN) через `/ip/route` + `/ip/firewall/connection`. На практике на роутере
с полной BGP-таблицей и активным conntrack это оказалось достаточно дорого,
чтобы на несколько секунд блокировать сам REST API роутера — из-за этого
следующий цикл опроса (`system/resource`+`/interface`, таймаут 8с) не
успевал, и роутер ошибочно помечался `down`. Раз стабильность сбора важнее
этой конкретной разбивки — убрал её полностью, коду просто нечего терять на
недоступности роутера.

**Что вместо неё:**
- **Кто нагружает сеть** — уже дёшево закрыто «Топ Wi-Fi»/«Топ Ethernet»,
  без единого лишнего запроса к роутеру
- **Где узкие места** — счётчики Firewall с эвристикой позиции в цепочке
- **Общая картина по каналам (провайдер/VPN) для роутера в целом** —
  бесплатно доступна во вкладке «Мониторинг»: отметьте галочками нужные
  WAN/VPN интерфейсы (по именам вроде `BrillteleCOM`, `L2TP-NDL`), и увидите
  их долю трафика — те же данные, что собирались бы для классификации,
  только без conntrack/route-lookup
- **Пакетов/сек (pps) на клиента** — добавлено вместо убранного: CAPsMAN
  отдаёт `packets` тем же способом, что и `bytes` (подтверждено на реальных
  данных), так что pps считается бесплатно, из уже собираемых данных.
  Резкий рост pps без роста kbps — типичный признак сканирования портов
  или флуда мелкими пакетами. Показывается в деталях клиента.

**На будущее, если понадобится «кто чаще всего попадает в drop firewall»** —
самый дешёвый путь без conntrack/route-lookup: добавить `log=yes` на
конкретные drop-правила в firewall и читать `/log` (системный журнал
RouterOS — ограниченный кольцевой буфер, в разы дешевле conntrack). Это
требует правки конфигурации на самом роутере, поэтому пока не реализовано —
скажите, если хотите пойти этим путём, и пришлите пример записи `/log`
после включения `log=yes` на одном правиле, чтобы я подстроил парсинг под
точный формат (как обычно, не имея доступа к вашему железу для проверки).

## Ускорение «Детали клиента»

Раньше поиск клиента в CAPsMAN → локальном Wi-Fi → legacy wireless шёл
**последовательно** — на медленном/недоступном роутере (например, за
GRE-туннелем) каждый шаг мог отвалиться только по таймауту, и они
складывались. Теперь все источники (CAPsMAN, локальный Wi-Fi, legacy
wireless, DHCP, ARP) запрашиваются параллельно — итоговое время ограничено
самым медленным *одним* запросом, а не суммой всех. Ошибки каждого источника
теперь попадают в лог (см. выше) вместо тихого исчезновения.

## Меньше нагрузки на роутер за цикл опроса

Диагностировано по логам: каждый цикл опроса одного роутера раньше делал
**~11 отдельных HTTPS/TLS-запросов** — интерфейсы, DHCP-аренды и ARP
опрашивались независимо в трёх разных функциях (мониторинг, Wi-Fi клиенты,
Ethernet клиенты, DHCP first-seen), каждая по-своему. На встроенном
веб-сервере RouterOS это иногда вызывало прерывистые таймауты
(`timeout of 5000ms exceeded`) — роутер физически не успевал.

Переписано на общий сбор данных раз за цикл: system resource + интерфейсы
запрашиваются один раз, DHCP-аренды и ARP — тоже один раз, и передаются во
все нуждающиеся в них функции. Итого — около 7 запросов на цикл вместо 11
(уникальные для каждой фичи остались: CAPsMAN registration-table, bridge
host table, neighbor discovery). Если роутер недоступен на этапе
system-resource — остальные фичи в этот цикл вообще не опрашиваются
(чтобы не долбить и без того недоступный роутер), статус сразу `down`.

Дополнительно: `bridge host table`/`neighbor discovery` (Ethernet-клиенты)
и учёт первого появления по DHCP не критичны к секундной свежести — теперь
опрашиваются раз в 2 и 4 цикла соответственно, а не каждый раз. Таймаут
запроса к роутеру увеличен с 5 до 8 секунд — на роутере с полной BGP-таблицей
(сотни тысяч маршрутов) 5 секунд иногда было мало даже для лёгких запросов.

## Топ адресов/портов клиента — вернул, но дёшево

RouterOS фильтрует conntrack по `src-address` на своей стороне
(`/ip/firewall/connection?src-address=<ip>`) — мы больше не тянем всю
таблицу и не делаем route-lookup поверх неё. Показываются только
адрес/порт/протокол/байты, без определения исходящего интерфейса.

## SSH-терминал

Вкладка «Терминал» — обычный интерактивный RouterOS CLI прямо в браузере
(через `xterm.js` + WebSocket-прокси на бэкенде к SSH роутера, порт 22, тем
же логином/паролем, что и REST API). Копипаста работает как в любом
терминале — выделение мышью копирует, вставка через Ctrl+V/правый клик.
REST API не поддерживает интерактивный шелл, поэтому именно SSH — он и так
обычно включён на роутере.

## Схема сети — дерево + список проблем

Переработал под задачу «искать узкие места и неисправности», не просто
рисовать картинку. Собирается целиком из уже опрашиваемых данных — без
ping/traceroute, без живых запросов к таблице маршрутов или conntrack:

- **Каналы** (☁️) — отмеченные во вкладке «Мониторинг» WAN/VPN интерфейсы
- **Точки доступа** (📶) и их клиенты (📱) — из «Топ Wi-Fi»
- **Проводные устройства** (🖥️) — порты с одним точно определённым MAC
- **Порты с несколькими устройствами / соседями** (🔌) — общие/аплинк-порты
- **Соседи** (Neighbor Discovery) — справочно, отдельным списком

Сверху — **список найденных проблем**, эвристики по уже собранным данным:
- канал не в статусе `up`
- Wi-Fi клиент со слабым сигналом (< −75 dBm)
- аномально высокий pps без роста трафика (возможен флуд/скан)
- порт с 4+ устройствами за одним аплинком (потенциальное узкое место)

«Жив ли сосед» на схеме — по-прежнему эвристика (виден в ARP), не
настоящий ping.

## Схема сети — org-chart дерево + клик-детали

Ещё раз переделал под «читается и несёт смысл», отказавшись от ручного
SVG-масштабирования (оно съедало читаемость при сжатии). Теперь — обычное
иерархическое дерево на CSS (классический приём с угловыми
соединительными линиями), без сжатия текста: карточки всегда в реальном
размере, при большом количестве узлов появляется горизонтальная
прокрутка — это нормально для органайзер-диаграмм с полусотней узлов.

**Клик по любому узлу** открывает окно с максимумом собранных данных:
- Wi-Fi клиент → то самое окно «Детали клиента» из «Топ Wi-Fi» (вендор по
  MAC, когда подключился, топ адресов/портов, график, всё как есть)
- Остальные узлы (каналы, проводные устройства, порты) → таблица всех
  полей, которые для них реально собраны (IP/MAC/порт/скорость и т.д.)

## Схема сети — вертикальный список веток

Горизontальное дерево с прокруткой вбок оказалось неудобнее, чем просто
вертикальный список — переделал: каждая группа (каналы, проводные
устройства, порты, точки доступа с их клиентами) идёт своим блоком сверху
вниз, дочерние элементы внутри блока переносятся по ширине экрана
(flex-wrap), не вылезая за края. Растёт страница вниз, а не вширь — обычная
вертикальная прокрутка. Клик по узлу — то же самое окно с деталями, что и
раньше.

## «Проверить связь» / «Удалить роутер» — перенесены в «Настройки»

Раньше висели в шапке карточки роутера на каждой вкладке — не нужны на
Мониторинге/Wi-Fi/Схеме сети и т.д. Убрал оттуда, оставил только бейдж
статуса. Обе кнопки теперь в верху вкладки «Настройки», рядом с остальными
действиями над самим роутером.

## Документация в приложении

Пункт «Документация» в ☰ меню (виден всем) — все шаги настройки роутера,

отдельный API-пользователь, SSH для терминала, требования для Wi-Fi/
Ethernet/DHCP статистики, частые ошибки и их причины.
